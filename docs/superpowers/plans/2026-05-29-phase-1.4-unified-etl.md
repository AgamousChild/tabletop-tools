# Phase 1.4 — Unify the Content ETL (scope)

> Spec: `2026-05-28-content-silo-bridge-design.md` (§5.1 crosswalk model — stable + incremental, validation-gated, append-only). Parent plan: `2026-05-28-unified-data-build-plan.md`. Worklist: `2026-05-29-data-layer-worklist.md`.
> Builds on Phase 1.1 (canonical content ids in `apps/data-import/server/src/lib/id-mapping.ts` — 99.99% reference resolution on live data).
> Principle: **additive first, validate against real data (match rates / counts), then cut over.** Brain node ids never change. Existing crosswalk links are never silently overwritten. No GW content committed.

---

## Goal

Collapse the two content ETLs (`data-import` + `brain/build-graph`) into one producer that writes R2 canonical content docs and populates the `content_entity` index. `game-data-store` consumes the docs as a projection; `brain/build-graph` consumes them for content payload. The `content_node_link` crosswalk bridges brain node ids ↔ canonical ids using the **stable + incremental, validation-gated** model from spec §5.1 — once a link is established it is never silently overwritten; re-keys are new rows that reference the prior link and only become active after a validation step (admin in a UI, or LLM evaluator) confirms the new link is genuinely a better fit.

---

## Current state (verified)

- **data-import** (Cloudflare Worker): Wahapedia CSV + BSData XML → `id-mapping` (BSData-canonical datasheet ids; Phase 1.1 canonical ids for ability / stratagem / enhancement / mission) → `data/*.json` in R2 → browser `game-data-store` (IndexedDB). Entry: `apps/data-import/server/src/lib/sync.ts`.
- **brain/build-graph** (`apps/brain/server/src/build-graph.ts`, ~1100 lines): reads a **separate static copy** of the Wahapedia JSON at `apps/data-import/client/public/wahapedia/`, plus GW markdown + community + Chapter Approved → ~25k `Node` docs → R2 BRAIN bucket. Vectorize index keyed on node id.
- **The silo:** same content produced twice; brain's static copy can drift from the live import.
- **Already aligned:** brain datasheet node `id` == `datasheetId` == BSData GUID == canonical datasheet id (`lib/parsers/game-data.ts:437`). For datasheets the brain ↔ canonical link is identity.
- **Tables exist** (`schema.ts`, migration `0001`, prod): `content_entity`; `content_node_link`. `scoring_mission`, `game_state`, `mission_game_state` already FK `content_entity`.
- **`content_node_link` today:** the only writer is `scripts/11th-ingest/build-brain-nodes.mjs` — and it uses `ON CONFLICT(brain_node_id) DO UPDATE SET canonical_id=excluded.canonical_id`, which silently overwrites prior mappings on every run. **That's the bug the new crosswalk model fixes.**

## Target

```
            Wahapedia CSV + BSData XML
                      │
            one content producer (extends data-import worker — has both sources in memory)
                      ├─► R2 canonical docs  content/{type}/{id}.json   (source of truth + public surface)
                      └─► content_entity index rows (id/type/name/faction_id/parent_id/r2_key/dataslate_id + wahapedia_id/bsdata_id provenance)
                      │
   ┌──────────────────┴───────────────────┐
   ▼                                       ▼
game-data-store import = projection     brain/build-graph = consumes canonical docs for content payload;
of the canonical docs                   keeps its node ids; matcher proposes (brain_node_id → canonical_id) candidates;
(IndexedDB, unchanged keys)             candidates go through validation (admin UI or LLM evaluator);
                                        accepted candidates appended to content_node_link with prior_link_id reference
```

## Steps (ordered; each additive, each with a real-data gate)

1. **Schema migration on `content_node_link`.** Replace `brain_node_id` PK with synthetic `link_id` PK; add `prior_link_id` (self-ref FK), `validation_method`, `validated_by`, `validated_at`, `superseded_at`; index `brain_node_id`. Migrate the existing 11th-ingest rows to first-entry chain heads (`validation_method='auto-initial'`). **Gate:** existing rows preserved as chain heads; new schema applies; tests pass.

2. **Fix `scripts/11th-ingest/build-brain-nodes.mjs`.** Stop the `ON CONFLICT DO UPDATE` overwrite; insert as append-only under the new chain semantics. **Gate:** re-running the script does not modify existing rows; new candidates appear as new rows.

3. **Canonical content-doc producer — datasheets first.** Extend `runSync` in the data-import worker to emit `content/datasheet/{id}.json` to R2 alongside the existing `data/datasheets.json`. **Gate:** doc count == datasheet count; spot-check shape against a known datasheet.

4. **`content_entity` populate for datasheets.** Idempotent upsert from the producer. Add `wahapedia_id` / `bsdata_id` provenance columns to `content_entity` (Phase 1.1 principle). **Gate:** row count == datasheet count; FK integrity; re-run is a no-op.

5. **Producer + `content_entity` for weapons** (`parent_id` → datasheet). **Gate:** counts + FK + idempotent.

6. **Producer + `content_entity` for factions / subfactions / detachments** (the `dim_*` data folds in here). **Gate:** counts + FK + idempotent.

7. **Producer + `content_entity` for abilities / stratagems / enhancements** (using Phase 1.1 canonical ids). **Gate:** counts + FK + idempotent; cross-check against `validateContentIds` resolution rate (already 99.99% on raw Wahapedia).

8. **Wire `validateContentIds` counts into `runSync`** so every live import logs match / unmatched / ambiguous. **Gate:** live import emits the counts; ambiguous > 0 surfaces as a flag, not silently absorbed.

9. **Crosswalk validation process — admin UI + LLM evaluator path.** Admin sees pending candidate links (new + re-keys) with the reasoning (match method, confidence, prior link if any); can approve or reject. LLM evaluator runs the same gate for batched candidates (e.g., 11th-ingest's bulk imports). Approved → appended to `content_node_link` (prior superseded). Rejected → never become active. **Gate:** end-to-end flow proven on a small batch (admin approves N, LLM approves M, R rejected; counts match).

10. **Repoint brain build-graph to the canonical docs.** Brain stops reading the static `client/public/wahapedia/` copy; reads canonical docs from R2 instead. Brain keeps its node ids and scheme. The matcher proposes `(brain_node_id → canonical_id)` candidates → step 9 validation → appended to `content_node_link`. **Gate:** brain build output diff = content payload identical-or-improved; **brain node ids unchanged**; Vectorize unaffected; new crosswalk rows appended (none silently overwritten).

11. **Repoint `game-data-store` import to the canonical docs** (projection). Either the browser pulls canonical docs, or the producer keeps emitting `data/*.json` sourced from the canonical layer (zero client change). **Gate:** IndexedDB store keys/shape identical; consumer apps (versus, list-builder) unaffected (1.1 fields already additive).

12. **Retire the duplicate derivation.** Once 10 + 11 validated, remove brain's standalone Wahapedia copy/derivation. One content pipeline + a brain knowledge layer remain. **Gate:** one pipeline; brain knowledge layer only on top.

---

## Blast radius / risks

- **Two LIVE pipelines + deployed workers.** Brain Vectorize index is keyed on node id → **node ids MUST NOT change.** Crosswalk is append-only; brain ids are never rewritten.
- The static brain copy at `apps/data-import/client/public/wahapedia/` may already be **stale** vs the live import — reconcile before cutover (diff first).
- The 11th-ingest crosswalk rows in prod were written with the broken overwrite semantics. Step 1's migration preserves them as first-entry chain heads (`validation_method='auto-initial'`). From there forward, every re-key must pass step 9's validation.
- **Additive-first:** produce canonical docs + `content_entity` + new-shape crosswalk *alongside* existing outputs; validate match rates; cut consumers over only after each step's gate passes. Every step reversible.
